# gam-mcp 0.6.0 — Correct Numbers, Honest Results, Ready for HTTP

**Date:** 2026-09-17
**Status:** Draft for owner review
**Scope:** fixes to 0.5.2 found while evaluating it as a data source for an auditable analytics agent (`ask-data-agent`), plus what running as a shared HTTP sidecar requires. SDK v1 throughout.

## Why

`ask-data-agent` holds every published number to one rule: it must trace back to a real query result, and every caveat must reach the reader. A review of 0.5.2 against that rule (2026-09-17) found tools that return wrong or partial numbers with nothing in the result saying so. A live probe of the production network the same day settled what the API documentation left open (see [Evidence](#evidence-live-probe-2026-09-17)).

## Goals

- Every number a tool returns is either what GAM returned or a labelled computation whose inputs are in the same result.
- Nothing that qualifies a number (partial pages, warnings, time zone, currency, cache age) can be separated from it.
- A shared HTTP sidecar serving several callers is safe: no shared mutable state, no duplicate report jobs, no unauthenticated access when a token is configured.
- Each fixed defect has a test that failed on 0.5.2.

## Non-goals

- Migrating to MCP TypeScript SDK v2 (`tasks/todo.md`, planned separately; it follows this release).
- `outputSchema` / `structuredContent`.
- New analytical tools.
- Anything in `ask-data-agent` (its port gets its own design once 0.6.0 is released).

## Decisions settled with the owner

- **D-1 — One report path first.** A single `executeReport()` replaces the seven polling loops before any other fix, so each fix is written once.
- **D-2 — Pages, not files.** Large results come back as pages with a stateless cursor, in both stdio and HTTP mode. `file_path` output is removed everywhere.
- **D-3 — Saved queries are stdio-only.** HTTP mode does not register `save_query`, `list_saved_queries`, `run_saved_query` or `delete_saved_query`.
- **D-4 — `GAM_TIMEZONE` is honoured.** The owner's deployment deliberately sets a date zone that differs from the zone the network reports; this is correct and must keep working. §2.4 defines what the setting controls, given what GAM allows.
- **D-5 — SDK v1.** The hand-built zod→JSON-Schema converter is extended, not replaced; the v2 migration deletes it later.
- **D-6 — Full `admanager` scope stays.** The `admanager.readonly` scope cannot create reports (probe). Read-only behaviour is enforced by what the client can send (§2.3, test H7), not by the OAuth scope.

## Evidence: live probe, 2026-09-17

Run against the owner's production network with their service account, script `tasks/probe-0.6.ts` (uncommitted). Two HIDDEN report objects were created; the API has no delete. The network code, the report ids and the network's own time zone and currency are deliberately not recorded here — the observations below are about the API's shape, which is what this spec needs.

| `admanager.readonly` | `networks.get` succeeds; `reports.create` fails `403 ACCESS_TOKEN_SCOPE_INSUFFICIENT` |

Two conclusions shape the design: line-item attributes such as lifetime impressions and the delivery indicator are **live values at `runTime`**, not values as of the report's end date; and a report cannot be computed in a zone other than the network's for ordinary metrics.

## 1. Result format

### 1.1 Report results

Every tool that returns report rows returns this shape. Keys are written in this order, so anything that truncates the serialized text keeps the qualifiers and loses rows first:

```json
{
  "summary": "Top 20 advertisers by revenue, 2026-09-01..2026-09-16 (20 of 46, sorted by REVENUE desc)",
  "provenance": {
    "network_code": "<network>",
    "report_type": "HISTORICAL",
    "report": "networks/<network>/reports/<report>",
    "result": "networks/<network>/reports/<report>/results/<result>",
    "run_time": "2026-09-17T04:48:39Z",
    "date_range": { "start": "2026-09-01", "end": "2026-09-16" },
    "report_time_zone": "Asia/Tokyo",
    "date_time_zone": "Asia/Seoul",
    "currency_code": "USD",
    "dimensions": ["ADVERTISER_ID", "ADVERTISER_NAME"],
    "metrics": ["REVENUE"],
    "filters": [],
    "sort": [{ "field": { "metric": "REVENUE" }, "descending": true }],
    "cache": { "hit": false }
  },
  "total_row_count": 46,
  "returned_row_count": 20,
  "truncated": false,
  "next_cursor": null,
  "warnings": [],
  "schema": [
    { "name": "ADVERTISER_ID", "type": "integer" },
    { "name": "ADVERTISER_NAME", "type": "string" },
    { "name": "REVENUE", "type": "number" }
  ],
  "rows": [ { "ADVERTISER_ID": 4000001, "ADVERTISER_NAME": "Example advertiser", "REVENUE": 1234.5 } ]
}
```

- `date_range` is GAM's computed `dateRanges[0]` from the first page, not the input echoed back.
- `run_time` is GAM's `runTime`. Values that GAM computes live (lifetime counts, delivery indicator) are valid as of this instant; tools that return them add a warning saying so.
- `truncated` is `true` when this page leaves more of the result to fetch: `next_cursor` is non-null, or `total_row_count` is known and greater than the rows returned so far (this page's plus any earlier pages'). It is unconditionally `false` when a `top_n` input capped the fetch — the cap is a deliberate stop short of the rest of the result, not a page boundary, so there is no cursor to resume it with (`pageEnvelope`'s `capped` branch) — and `false` for every derived/computed result (`compare_periods`, `diagnose_fill_rate`, `diagnose_floor_pricing`, `find_anomalies`; `derivedEnvelope` sets it `false` unconditionally), which returns its whole computed output as one page. A `top_n`-capped result states its cap as "N of total" in `summary` instead.
- `cache.hit` is `true` when the rows came from a result produced by an earlier call; `run_time` then shows when that result was computed.
- `dimensions`, `metrics`, `filters` and `sort` are copied from the report definition GAM ran, in GAM's own shapes (`filters` are `fieldFilter` objects, `sort` entries name a `field.metric` or `field.dimension`). Translating them back into tool-input form would lose information, so provenance doesn't.
- `total_row_count` is `null`, with a warning, when GAM doesn't report a count and more pages exist. GAM's JSON omits zero values, so a missing count on a first page with no further page means the rows on that page are all there is.

### 1.2 Values

Rows are built directly from `fetchRows`. The CSV round trip, `readCsvGz`, `createOutputManager` and the temp directory are deleted.

| GAM `ReportValue` | JSON value | `schema.type` |
|---|---|---|
| `intValue` within ±2^53 | number | `integer` |
| `intValue` outside ±2^53 | string, plus one warning naming the column | `integer` |
| `intValue` for a dimension whose schema type is a date (`YYYYMMDD`) | `"YYYY-MM-DD"` string | `date` |
| `doubleValue` | number | `number` |
| `stringValue` | string | `string` |
| `boolValue` | boolean | `boolean` |
| `intListValue` / `doubleListValue` / `stringListValue` | array | `array` |
| `bytesValue` | base64 string | `bytes` |
| absent or empty | `null` | type from the schema |

Column names and order come from the report definition (dimensions, then metrics), never from process memory. For an open-ended line item, the end date is `null` when `LINE_ITEM_UNLIMITED_END` is true; tools that show flight dates request that dimension alongside the end date.

### 1.3 Pages

A new tool, `fetch_report_page`, takes one argument, `cursor`.

- The cursor is base64url JSON: `{ "v": 1, "result": "…", "page_token": "…", "offset": 5000, "total_row_count": 12345, "run_time": "…", "date_range": {…} }`. It carries what GAM returns only on the first page; everything else in `provenance` (dimensions, metrics, filters, sort, currency, report type) and the column order come from `reports.get` on the parent report, cached in memory by report name.
- `result` must match `networks/<configured network>/reports/<digits>/results/<digits>`; anything else, or a cursor that isn't valid base64url JSON, is `INVALID_INPUT`. The cursor is not signed: it grants nothing the same service account couldn't obtain by running the report.
- A result GAM no longer serves (404, or `NOT_FOUND`/`FAILED_PRECONDITION` naming the result) is `REPORT_RESULT_EXPIRED` with the hint "re-run the tool that produced this cursor".
- Page size is `GAM_PAGE_ROWS` (default 5,000). GAM caps `pageSize` at 10,000, so larger settings are clamped and startup logs the clamp once.

### 1.4 Tools that compute from rows

`compare_periods`, `pacing_status`, `find_anomalies`, `find_unused_ad_units`, `diagnose_fill_rate` and `diagnose_floor_pricing` compute their output from one or more reports, so they have no GAM result to page through.

- They read every page of their input reports. If an input report has more than **50,000** rows (`ponytail:` a constant; raise it or add paging of derived output if a real network needs more), or their own output exceeds `GAM_PAGE_ROWS`, they return `RESULT_TOO_LARGE` asking the caller to narrow the query. They never return a cut-down result.
- Their `provenance` lists every input report (`inputs: [{ report, result, run_time, date_range }]`) instead of a single `report`/`result`.
- Every computed field lives under a `derived` object per row, with `method` (one sentence), `heuristic: true|false`, and the input values it was computed from. `null` inputs make the output `null`; a warning counts how many rows had a `null` input. `numOr0`, `pctOrZero` and `Number(x) || 0` are removed.

### 1.5 Errors

- Every error reaches the client with `isError: true`: unknown tool, invalid input, an error envelope returned by a handler, and an exception.
- The body stays `{ "error": { "code", "message", "hint", "details" } }`.
- New codes: `REPORT_RESULT_EXPIRED` (§1.3), `RESULT_TOO_LARGE` (§1.4), `DUPLICATE_JOIN_KEY` (§4.1).

## 2. The shared report path

### 2.1 `executeReport(ctx, request)`

One function in `src/report-exec.ts` owns the whole path. In order:

1. Validate the query (§3), including `validateCombo` for every caller.
2. Compute the definition hash (§2.2).
3. If an identical run is in flight in this process, await it (§2.6).
4. If the cache has a live result for the hash, fetch the requested page from it (§2.5).
5. If the cache has a timed-out operation for the hash, resume polling it (§2.6).
6. Find or create the report (§2.2), run it, poll it.
7. Fetch the first page (or every page, for §1.4 tools) and build the result (§1).

Polling starts at 2 s, multiplies by 1.5 and stops growing at 15 s. `report-run.ts` (`runAndRead`, `numOr0`, `pct`) and the seven local loops are deleted. The `reportQueryCache` map in the REST client is deleted.

### 2.2 Reuse and labelling

- **Definition.** The object sent as `reportDefinition`: dimensions, metrics, filters, custom dimension key IDs, report type, fixed date range, `timeZoneSource`, `currencyCode`, sorts.
- **Hash.** SHA-256 of a canonical JSON of the definition. Dimension and metric order is kept: GAM returns each row's values in that order, so the columns follow it and a request that only reorders them is a different report. Filter order is normalised. A filter's value list is sorted only for set operations (`IN`, `NOT_IN`, `CONTAINS`, `NOT_CONTAINS`); other operations' values are positional (`BETWEEN`'s bounds) and keep their order. `customDimensionKeyIds` keep their order (they are positional). The cache key and the report name use this same function.
- **Name.** `gam-mcp <first 16 hex chars of the hash>` as `displayName`. Reports stay `HIDDEN`.
- **Find or create.** Look up the hash in an in-memory map (bounded, 1,000 entries, least recently used dropped). On a miss, `reports.list` with `filter=displayName = "<name>"`. A listed report is reused only if its stored `reportDefinition` equals ours after the same normalisation; otherwise create a new one. If GAM rejects the filter, log it once per process and create.
- The number of report objects in the network grows with the number of distinct definitions, not the number of calls. They cannot be deleted through the API; this is stated in the README.

### 2.3 Retries

- `GET` requests are retried on network errors, 429 and 5xx, as today.
- `POST` requests are retried **only on 429**, which means GAM did not process the request. A 5xx or network error on `reports.create` or `:run` is returned as an error. If the create did happen, the next identical call finds the report by name.
- The client can issue exactly two kinds of POST: `networks/{code}/reports` and `networks/{code}/reports/{id}:run`. Test H7 holds this.

### 2.4 Identity, scope and time zones

- **Scope.** `https://www.googleapis.com/auth/admanager` (D-6). No setting.
- **Startup check.** Before serving, call `networks.get`. Failure stops the process with exit code 2 and a message naming the credential *source* (`file`, `json`, `adc`) and GAM's status, never key material. This applies to stdio and HTTP.
- **Report time zone.** Every report uses `timeZoneSource: PUBLISHER`: the network's zone, the only source GAM accepts for these reports (probe). The network's zone is recorded as `report_time_zone`.
- **Date time zone.** `GAM_TIMEZONE` chooses calendar dates: what "yesterday" is, how relative ranges resolve, and the end-date check (§3.2). It defaults to the network's zone. It is recorded as `date_time_zone`.
  - An invalid IANA name stops startup, naming the setting.
  - A value different from the network's zone is accepted. Startup logs one `info` line naming both.
  - If the two zones have different UTC offsets on any day in a result's date range, the result carries a warning: the dates were chosen in `date_time_zone` but GAM's day boundaries are `report_time_zone`'s. Two zones that share a UTC offset and observe no daylight saving never warn, which is the case for the owner's deployment.
- **Currency.** Every report sets `currencyCode` to the network's primary currency, recorded as `currency_code`.

### 2.5 Cache

The cache remembers which GAM result answers a definition, not the rows.

- **Entry.** `done`: `{ report, result, run_time, date_range, total_row_count, stored_at }`, or `pending`: `{ report, operation, started_at }` (§2.6).
- **Hit.** For a `done` entry younger than `GAM_REPORT_CACHE_TTL_MS` (default 1 hour; `0` disables `done` entries), fetch the requested page from `result`. Warnings are rebuilt from the request, so a hit carries the same warnings as a miss. `provenance.cache.hit` is `true`, and `run_time` is the original.
- **Expired result.** If GAM no longer serves a cached result, drop the entry and run the report again, once. If the new result is also unavailable, return `REPORT_RESULT_EXPIRED`.
- **Bounds.** 1,000 entries in memory, least recently used dropped, TTL enforced in memory as well as on disk.
- **Disk tier.** `GAM_REPORT_CACHE_DIR` keeps working and stores the same small entries.

### 2.6 Shared runs and timeouts

- **Shared runs.** An in-flight map from hash to promise. A second identical call in the same process awaits the first. A failure is delivered to every waiter and removes the entry, so the next call starts fresh.
- **Timeout.** A run is recorded as `pending` for its hash the instant GAM accepts it, not after the timeout — so a call that ends any other way (a `REPORT_TIMEOUT` once `GAM_REPORT_TIMEOUT_MS` elapses, default 300,000; a poll request that itself fails; or the process being killed mid-poll) leaves the operation for the next identical call to resume, keeping the run's original start time. Only two endings forget the entry instead of restoring it: GAM reporting the run `failed`, and a poll `404` — the operation is gone, so `pollFailure` reports it under that same `REPORT_FAILED` code and it is forgotten the same way, not restored. `pending` entries expire after one hour.
- **Client disconnect.** In HTTP mode, a client that disconnects does not cancel polling; the result lands in the cache for the next call.
- **Quota.** A 429 while polling, after retries, is `QUOTA_EXCEEDED`, not `REPORT_FAILED`.
- The README tells deployers to set `GAM_REPORT_TIMEOUT_MS` below their client's call timeout.

### 2.7 HTTP boundary

- `GAM_HTTP_BEARER_TOKEN`: when set, every request except `/healthz` must carry `Authorization: Bearer <token>`, compared with `crypto.timingSafeEqual`; otherwise `401`. When unset, startup logs a warning once that the endpoint is unauthenticated.
- Request bodies over 1 MiB (1,048,576 bytes) get `413`; the server keeps serving.
- `GAM_HTTP_ALLOWED_HOSTS` (comma-separated host names, without ports): when set, a request whose `Host` header names another host gets `403`, checked before the token. The host name is compared without its port, as the SDK's `hostHeaderValidation` middleware compares it. The transport's own `allowedHosts` and `enableDnsRebindingProtection` options are deprecated in SDK 1.30 in favour of that middleware, which is written for Express, and they compare the whole header, port included, so the server does the check itself. When unset, no Host check.
- `/healthz` stays unauthenticated, skips the Host check, and returns only `{"status":"ok"}`. Because startup now checks the credential (§2.4), a running process has a working one.
- An invalid `GAM_HTTP_PORT`, `GAM_HTTP_BEARER_TOKEN` (anything but printable ASCII without spaces) or `GAM_HTTP_ALLOWED_HOSTS`, or a port another process holds, stops startup with exit code 2, naming the variable and never quoting the token.

## 3. Input checks

### 3.1 Schemas

- Every tool's input object is `.strict()`: an unknown key is `INVALID_INPUT` naming the key.
- The zod→JSON-Schema converter emits `description`, `default`, `minimum`/`maximum`, `minLength`/`maxLength`, `pattern`, `enum`, `format: date`, and `additionalProperties: false`. Every field has a description (test H5).

### 3.2 Dates

One `DateRangeInput` type, used by every tool that takes a range:

- Either `{ start, end }` or `{ relative }`.
- Absolute dates must match `YYYY-MM-DD` and be real calendar dates; `2026-02-30` and `banana` are `INVALID_DATE_RANGE`.
- `relative` accepts `yesterday`, `last_7_days`, `last_30_days`, `last_week`, `last_full_month`, `month_to_date`, `quarter_to_date`, `last_quarter`, `year_to_date`. **`today` is removed.**
- All resolution happens in `date_time_zone` (§2.4).
- Every range needs `start ≤ end`. What else applies depends on the report type:
  - Historical-family reports (`HISTORICAL`, `REACH`, `AD_SPEED`, `PRIVACY_AND_MESSAGING`): `end ≤ yesterday`. This includes the tools built with `buildReportTool` and the explicit comparison range of `compare_periods`.
  - `FUTURE_SELL_THROUGH` (`sell_through`): `start ≥ today`, because a past window returns nothing and an empty forecast must not read as zero. Relative ranges are not accepted for forecasts.
- `month_to_date`, `quarter_to_date` and `year_to_date` on the first day of their period return `INVALID_DATE_RANGE: no complete day in this period yet`.
- `previous_year` shifts each date back one calendar year and clamps the day to that month's length (`2028-02-29` → `2027-02-28`; a range ending on a month's last day keeps ending on that month's last day). `previous_period` keeps the equal-length window.
- Resolution errors are `INVALID_DATE_RANGE` envelopes, never thrown strings.

### 3.3 Names that match more than one entity

`kv_report` and the key-value resolver (`kv-rewrite.ts`) return `AMBIGUOUS_NAME` with `details.candidates` (ID and name) when more than one key or value matches, instead of using the first match.

### 3.4 Annotations

Every registered tool declares annotations explicitly:

- Report and lookup tools: `readOnlyHint: true`, `openWorldHint: true`.
- `health_check`, `usage_stats`, `describe_schema`, `list_saved_queries`: `readOnlyHint: true`.
- stdio only: `save_query` `readOnlyHint: false, destructiveHint: true` (it overwrites by name); `delete_saved_query` `readOnlyHint: false, destructiveHint: true`; `run_saved_query` `readOnlyHint: true, openWorldHint: true`.

`readOnlyHint: true` on report tools means "does not change anything a user of the network can see": the report objects they create are `HIDDEN`. The README says this.

### 3.5 HTTP mode tool set

The server builds its tool list per mode. HTTP mode omits the four saved-query tools; calling one returns `INVALID_INPUT: Unknown tool`.

## 4. Tool fixes

### 4.1 IDs beside names

Whenever a tool groups by advertiser, order, line item or ad unit, it requests the ID dimension with the name dimension (`ADVERTISER_ID` + `ADVERTISER_NAME`, `ORDER_ID` + `ORDER_NAME`, `LINE_ITEM_ID` + `LINE_ITEM_NAME`, `AD_UNIT_ID` + `AD_UNIT_NAME`). Grouping, sorting and joins use the IDs. `compare_periods` joins on the full dimension tuple; if a key still occurs twice in either period it returns `DUPLICATE_JOIN_KEY` instead of joining.

### 4.2 `top_n`

The seven tools in F1 put `sorts: [{ field: { metric }, descending: true }]` in the definition and fetch only the first `top_n` rows. `summary` states the sort and "N of `total_row_count`". The sort is part of the definition hash.

### 4.3 Pacing

gam-mcp stops computing its own pacing percentage. On the probe's mid-flight line item it would have reported 1.117 where GAM reports 1.027, and two conflicting pacing figures do more harm than one.

- `pacing_status` requests `LINE_ITEM_ID`, `LINE_ITEM_NAME`, `LINE_ITEM_TYPE`, `LINE_ITEM_PRIMARY_GOAL_TYPE`, `LINE_ITEM_PRIMARY_GOAL_UNIT_TYPE`, `LINE_ITEM_PRIMARY_GOAL_UNITS_ABSOLUTE`, `LINE_ITEM_START_DATE`, `LINE_ITEM_END_DATE`, `LINE_ITEM_UNLIMITED_END`, `LINE_ITEM_LIFETIME_IMPRESSIONS`, `LINE_ITEM_DELIVERY_INDICATOR` with `IMPRESSIONS` for the requested range. `pacing_status` gains an optional `date_range` defaulting to `last_7_days`: the indicator is a live value either way, the range only selects which line items appear, and a `month_to_date` default would fail on the first day of every month (§3.2).
- Each row reports `delivery_indicator` exactly as GAM returns it, **only** when the primary goal type is `LIFETIME`. Otherwise it is `null` with `derived.reason: "no lifetime goal"`.
- A warning states that `delivery_indicator` and lifetime impressions are live values at `run_time`, not values as of the range's end.
- Its description no longer says pacing is unavailable.
- `find_anomalies` pacing uses the same report over `last_7_days` and flags lifetime-goal line items whose `delivery_indicator` is below `threshold_pct / 100`, sorted by indicator ascending. `monthProgress` and the local `previousPeriod` are deleted.

### 4.4 Metric names

`inventory_breakdown` requests `REVENUE` and `IMPRESSIONS` (the REST names). `buildReportTool` runs `validateCombo`. Test H3 checks every dimension and metric that any tool can request against `schema-generated.ts` for its report type.

### 4.5 `find_unused_ad_units`

Considers only ad units whose status is `ACTIVE` and that have no child ad units, and states that rule in `warnings`. A unit absent from the report counts as zero ad requests, because GAM omits rows whose metrics are all zero; the warning says so.

### 4.6 Heuristics

- `diagnose_fill_rate` cause labels, `diagnose_floor_pricing`'s `est_opportunity`, and `find_anomalies`' fill-rate, eCPM and viewability flags move under `derived` with `heuristic: true`, a one-sentence `method`, and every input value used, including the `IMPRESSIONS` the fill-rate check reads.
- `est_opportunity` keeps its name; its `method` says it is an estimate and how it is computed.

### 4.7 Smaller fixes

- A failed `health_check` returns `isError: true` with the failing check named.
- Report summaries list the filters and sort.
- Bundled prompts use date inputs the tools accept and no longer ask for "estimated revenue impact".
- `describe_line_item` returns commercially sensitive fields (rates, budgets); the README says so, so clients can gate it.

## 6. Breaking changes

1. `file_path` and `preview_rows` are gone; large results are paged through `fetch_report_page`.
2. `row_count` is replaced by `total_row_count` and `returned_row_count`; row values are typed (§1.2); `schema` types are real.
3. Tools that compute from rows return `derived` blocks and refuse oversized inputs.
4. Unknown arguments are rejected.
5. Every historical date-taking tool rejects an end date after yesterday, and `sell_through` rejects a start before today; relative `today` is removed; period-to-date ranges on their first day are errors.
6. HTTP mode does not offer saved-query tools.
7. `pacing_status` and `find_anomalies` pacing report GAM's delivery indicator instead of a computed percentage.
8. `GAM_TIMEZONE` defaults to the network's zone instead of UTC.
9. Startup fails when the credential cannot read the network.
10. `GAM_TIMEZONE` must be an IANA time zone name. 0.5.2 passed the variable to `Intl` unvalidated, which accepts a raw UTC offset (`+08:00`, `-0500`); 0.6.0's `canonicalTimeZone` rejects anything `Intl` resolves to a string starting with `+` or `-`, and startup stops with exit code 2. `Etc/GMT-8` and similar stay accepted — they're spelled with a leading letter, so they're IANA names, not offsets.

## 9. Follow-ups and open items

- **Result retention.** Re-fetch the two report results the 2026-09-17 probe created after 24 hours and after 7 days and record the outcome here; their resource names are in the owner's local probe output and are deliberately not recorded in this repo. Until then, `REPORT_RESULT_EXPIRED` and the silent re-run (§2.5) cover any retention.
- **The owner's Claude Code configuration** runs `npx -y gam-mcp@latest`, so the breaking changes in §6 reach that session as soon as 0.6.0 is published. `GAM_TIMEZONE=Asia/Seoul` keeps working. The owner decides whether to pin `gam-mcp@0.5.2` until they are ready.
- **`PROVIDED` time zones** are not used. Revisit only if GAM makes them broadly compatible.
- **SDK v2 migration** (`tasks/todo.md`) follows this release; its Phase 0 baseline should be taken from 0.6.0.
- **The `ask-data-agent` port** gets its own design after release. Known inputs: `GAM_TIMEZONE=Asia/Seoul`; `GAM_REPORT_TIMEOUT_MS` below that client's 120 s call timeout; the bearer token passed as `${GAM_MCP_TOKEN}`; `describe_line_item` treated as sensitive.
- **A per-request GAM timeout.** Individual GAM REST calls carry no request-level timeout or `AbortController`; only the poll loop's overall `GAM_REPORT_TIMEOUT_MS` bounds a report run. The resume machinery already makes a short per-call deadline safe to add — a run is recorded `pending` the moment GAM accepts it (§2.6), so a call that times out restores the run instead of losing it.
- **Four tools have no `date_range` input and compute their window from the wall clock: `find_unused_ad_units`, `diagnose_fill_rate` and `diagnose_floor_pricing` take `lookback_days` and resolve it with `lastDays(lookback_days, …, ctx.now)`; `find_anomalies` takes no window input at all and always uses a hardcoded `lastDays(7, …, ctx.now)`.** All four reach GAM through `executeReportRows` → `firstPage` → `definitionHash`, whose `canonicalDefinition` includes `dateRange`, so each one's report definition — and therefore its hash — changes every calendar day it runs, and each new day's run defines a fresh, hidden, undeletable report (this server exposes no way to delete a report it created). Every other report tool (`ad_speed`, `bidder_breakdown`, `inventory_breakdown`, `fill_rate`, `consent_messaging`, `pacing_status`, and the rest) takes `date_range` and can be pinned to a fixed window. This is why PR 5's smoke check for `find_unused_ad_units` had to be gated behind its own opt-in flag instead of running with the rest of the smoke — one instance of a problem shared by all four tools, not a `find_unused_ad_units`-only quirk.
- **`find_unused_ad_units` should expose structured `listed`/`excluded` counts.** They currently appear only inside the human-readable `summary` string; the smoke check has to recover them with a regex because no structured field carries them.
- **`find_unused_ad_units` should confirm `AdUnit.hasChildren`.** Leaf-ness is currently derived only from `parentAdUnit` among the ad units actually listed, not from GAM's own `hasChildren` field, because that field is undocumented in this repository and unconfirmed by probe (`find_unused_ad_units.ts:61-67`). The cost: this derivation only sees the listed set, so a unit that looks like a leaf here may have children outside the scan — a caveat the tool's `max_units` warning already discloses.
- **The `derived.value` semantic ambiguity.** Depending on the tool, `derived.value` is a cause label (`diagnose_fill_rate`), an opportunity estimate (`diagnose_floor_pricing`), a drop magnitude (`find_anomalies`), or a delivery indicator (`pacing_status`) — one field, several meanings, distinguishable only by reading the row's `derived.method`. The same clarification should also settle `diagnose_floor_pricing`'s row shape, where `verdict` sits flat on the row while its paired opportunity estimate nests under `derived.value` instead of being its own field.
