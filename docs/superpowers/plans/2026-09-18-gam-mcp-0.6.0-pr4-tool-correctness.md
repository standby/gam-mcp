# gam-mcp 0.6.0 PR 4 — tool correctness Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the analytics tools tell the truth — honour `top_n`, put computed fields under `derived` with their method and inputs, group by ID as well as name, and report GAM's delivery indicator instead of a pacing figure gam-mcp invented.

**Architecture:** Four shared pieces land first and the tools then consume them: a typed `sort` that reaches the report definition (so it is in the definition hash for free), a `src/derived.ts` with null-propagating arithmetic, a `DUPLICATE_JOIN_KEY` error code with the code list exported rather than hand-copied, and a `derivedEnvelope` that is told the pre-slice total instead of counting the rows it was handed. Tasks 3–7 are then one tool family each.

**Tech Stack:** TypeScript (NodeNext, strict), zod for tool inputs, vitest, the GAM Ad Manager REST API v1. No new dependencies.

**Spec:** `docs/superpowers/specs/2026-09-17-gam-mcp-0.6.0-design.md` — PR 4 is §4 in full, plus §1.4 (`derived` blocks), §1.5's `DUPLICATE_JOIN_KEY`, and §1.2's unlimited-end rule. Tests I1–I14 come from §7.

**Scope source:** `tasks/pr4-scope.md` in the main checkout — every "wrong today" claim in Tasks 1, 2, 3 and 6 was executed against the built `dist/`, not inferred. Read it if a step's reasoning is unclear.

**Branch:** `feat/0.6.0-tool-correctness`, worktree `~/workspace/gam_mcp-0.6.0-pr4`, based on `feat/0.6.0-smoke` (PR #10, top of the stack). Base HEAD `68cf575`.

## Global Constraints

- **Generic-MCP (CLAUDE.md).** Never bake publisher-specific data into code, fixtures or prose. Test fixtures use network `1234` and invented entity names. Slot-based dimension descriptions say "publisher-configured slot N" and never imply a meaning. The `method` strings added in Task 5 state the *rule*, never an example network's values.
- **No AI attribution** in any commit message or PR body (CLAUDE.md lines 34–35). Before every commit run:
  `git log <base>..HEAD --format='%B' | grep -i -E '^(co-authored-by|.*generated with \[?claude|claude-session)'` — it must print nothing.
- **Never type a `\u` escape into an Edit/Write tool argument.** Tool arguments are JSON, so it decodes into a raw control byte in the source file. Use a `python3` script with `chr()`. Before every commit, scan changed files for control bytes other than tab; the scan must print nothing.
- **Absence is not permission.** The recurring defect class in this codebase: an empty, missing or unparseable value reaching an allow path. `Number('') === 0`, `?? ''`, an empty array satisfying `every()`. When a check can receive nothing, decide explicitly what nothing means and prefer refusal or `null`. This task list exists largely because `numOr0` did the opposite.
- **Mutation-test every new assertion.** Break the code the test covers, watch the test fail, restore. A test that has never been seen to fail is not evidence. Record the mutation and the observed failure in the task report.
- **stdout is the MCP channel.** Logs go to stderr. Never `console.log`.
- **Read/report only.** No tool gains a write or mutate operation.
- **Node >= 22**, `npm test` is `vitest run`, `npm run typecheck` is `tsc --noEmit`. Tests are **not** typechecked (`tsconfig.json` includes `src/**/*` only) — a type error in a test file is invisible, so assert shapes explicitly.
- **Commit style:** Conventional Commits. Tasks 1, 3, 4, 5 and 7 are breaking and their commits carry a `BREAKING CHANGE:` footer.

### Task 1: `top_n` sorts the report and caps the page

**Spec:** §4.2, §1.1 (the worked example at spec lines 88–110 is literally `top_advertisers({top_n: 20})`).

Today `buildReportTool`'s handler never reads `input.top_n` — `grep -n 'top_n' src/report-tool-builder.ts` returns nothing. `top_n` changes only the wording of `summary`. Executed against a 46-row deliberately unsorted fixture, `top_advertisers({top_n: 20})` returned all 46 rows in fixture order with `provenance.sort: []` while the summary said "Top 20".

**Files:**
- Modify: `src/gam-client.ts` — `ReportQuery` gains `sort?`
- Modify: `src/report-definition.ts` — map `query.sort` to GAM's `sorts`
- Modify: `src/report-tool-builder.ts` — `ReportToolConfig` gains `topN` and `sort`
- Modify: `src/report-exec.ts` — `ReportRequest` gains `topN`; suppress cursor/truncated; append the sort clause to `summary`
- Modify: `src/tools/top_advertisers.ts`, `top_line_items.ts`, `kv_breakdown.ts`, `bidder_breakdown.ts`, `yield_breakdown.ts`, `video_breakdown.ts`, `viewability_breakdown.ts`
- Test: `tests/tools/top_n.test.ts` (new, I1)
- Test: `tests/report-key.test.ts` (extend — B1 fixture gains `sorts` + a positional test)

**Interfaces:**
- Produces: `ReportQuery.sort?: { metric: string; descending: boolean }` — consumed by Task 7's summary path.
- Produces: `ReportRequest.topN?: number` — nothing later consumes it.
- Produces: `ReportToolConfig.topN?: (input) => number | undefined` and `ReportToolConfig.sort?: (input) => { metric: string; descending: boolean } | undefined` — Task 3 edits the same seven tool files and must not drop these.

**The rule that makes this correct:** `top_n` must **not** reach the report definition. The definition is hashed to name and reuse the report (`src/report-key.ts`), so a `top_n` in it would fragment the cache — two calls differing only in `top_n` would define and run two separate GAM reports, each one HIDDEN and undeletable. The *sort* does belong in the definition (§4.2's last sentence); the *count* belongs to the fetch.

- [ ] **Step 3: Write `src/derived.ts`**

```ts
// Arithmetic for tools that compute from report rows (spec §1.4).
//
// The rule that matters: absence is not zero. numOr0/pctOrZero/Number(x)||0
// turned a missing metric into 0, which then read as a real measurement -- a
// line item with no AD_REQUESTS became a 0% fill rate rather than an unknown
// one. Everything here propagates null instead.

// A report cell as a number, or null when it is absent or not numeric.
export function num(cell: unknown): number | null {
  if (typeof cell === 'number') return Number.isFinite(cell) ? cell : null;
  if (typeof cell !== 'string') return null;
  const trimmed = cell.trim();
  if (trimmed === '') return null;
  const n = Number(trimmed);
  return Number.isFinite(n) ? n : null;
}

// a / b, or null. A zero denominator yields null, not 0: no impressions means
// the rate is unknown, not that it is zero.
export function ratio(a: number | null, b: number | null): number | null {
  if (a === null || b === null || b === 0) return null;
  const r = a / b;
  return Number.isFinite(r) ? r : null;
}

export type Derived = {
  value?: unknown;
  method: string;
  heuristic: boolean;
  inputs: Record<string, unknown>;
};

// One shape for every derived block, so rows are comparable across tools.
export function derived(d: Derived): Record<string, unknown> {
  return { value: d.value, method: d.method, heuristic: d.heuristic, inputs: d.inputs };
}
```

### Task 8: a filter may use the same alias its dimension does

**Spec:** none directly — this is a pre-existing bug found in PR 3 task 5's review (`progress.md:31`). The governing rule is the existing code's own stated intent: "We accept the familiar name and rewrite it so a caller asking for 'CREATIVE_SIZE' gets data instead of a 400 from GAM" (`src/schema.ts:66-68`). Today that promise holds for dimensions and breaks for filters.

**Depends on:** nothing. It could be done first as a warm-up or dropped from PR 4 without consequence.

Executed:

```

             filters: [{ field: 'CREATIVE_SIZE', op: '=', value: '300x250' }] })
-> INVALID_INPUT  "Unknown filter dimension: CREATIVE_SIZE"
```

The dimension resolved to `RENDERED_CREATIVE_SIZE` and would have worked; the identically-spelled filter sank the call. The message is actively misleading — it says the name is unknown when the server knew it well enough to rewrite it one line earlier.

**Decision — the shared shape, not the narrow one.** `resolveDimensionAlias` is called in **exactly one place** in `src/` (`run_report.ts:52`). `compare_periods.ts:41` and `saved_queries.ts:49` validate dimensions with no alias pass, so `compare_periods({ dimensions: ['CREATIVE_SIZE'] })` fails too. A 10-line fix in `run_report` would leave the asymmetry that produced this bug. Build `canonicalizeQuery` instead (~40 lines) and call it from all three.

**Do not put it inside `executeReport`.** Rewriting a name after the definition is built would change the hash silently and make the warning hard to attach to the right result.

**Files:** `src/schema.ts`, `src/tools/run_report.ts`, `src/tools/compare_periods.ts`, `src/tools/saved_queries.ts`; `tests/schema.test.ts`, `tests/tools/run_report.test.ts`
